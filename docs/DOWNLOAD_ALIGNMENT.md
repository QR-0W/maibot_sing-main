# Download alignment audit (offline, isolated checkout)

Baseline `xiaocutedog/maibot_sing-main` commit `4a72783` was available locally. Its `services/pipeline.py` and `music/search.py` are byte-identical to this checkout at HEAD (`git diff 4a72783 HEAD --` on those paths); its original `plugin.py` was read separately from that commit. This documents implementation behavior, not a live provider test or a claim of permission to download any specific recording.

## Original Mai-sing flow

- `plugin.py` resolves a default platform (`163` or `qq`) and calls `Pipeline.cover_song(query, sid, platform, search_limit, ...)`. Both the `/翻唱` command and `cover_song` tool use the same path. The declared `_pending` list/lock does not implement a selection UI; the command parses an unstructured query, not an album or ID.
- `services/pipeline.py:56-84` calls `music.search(query, platform, limit=5 by default)`, takes **results[0]**, obtains a URL by its song ID/platform/media ID, downloads response into memory using aiohttp (120-second total timeout), passes whole bytes to RVC, then returns audio. There is no exact-title/artist comparison, album chooser, byte cap, duration/format check, entitlement proof or ambiguity handling there. Search ordering is not proof of studio provenance.
- `music/search.py:668-746` uses NetEase `/api/search/get/web` or authenticated QQ Desktop search via `musicu.fcg`; each result contains platform, stable song ID, name, artists and album (QQ additionally media ID), **not duration or byte size** in the `SongInfo` adapter. `get_song_url` (`:758-880`) tries NetEase eapi, web player URL, then outer-link redirect; QQ vkey tries FLAC then MP3 then M4A and chooses the first nonempty `purl`. URL availability is not proof of a complete playable track or rights.
- NetEase search is anonymous by default; configured `MUSIC_U`/`__csrf`, validated cached cookie, explicit admin QR/cookie login, or configured account/password login can authenticate it. The original `plugin.py` attempts password login at startup **only if configured**, and checks reusable cached cookies; QQ search requires `uin` and `qqmusic_key` (configured or admin QR login/cache). These are music-provider credentials, independent of QQ chat/NapCat login. Do not trigger login, restore sessions or send chat messages as part of this audit. A legitimate login does not grant permission to bypass provider restrictions.

## Current 0.3.1 versus upstream

`runtime/worker.py:100-137` uses musicdl's NetEase client with a native-only parser override (third-party unlock parsing disabled), bounded search/download, exact normalized title/artist, duration and size filtering, and excludes some obvious title/album tags. Unlike upstream it cannot pick QQ, use upstream music cookies/session, or offer a song chooser. `worker.py:60-97` then sorts by duration and calls the largest 4-second cluster a studio master when it beats runner-up and has >=2 results. **This is unsafe**: a Pinkpop live take appears in the presumed studio-duration cluster; multiple catalog releases can repeat a live performance, while studio mixes can differ in duration. Text tags, compilation count, duration, shortest track and popularity do not establish recording identity. Its `source.json` selection reason can falsely claim a studio master. Neither this document nor the helper changes worker behavior yet.

## Pure helper contract and Lead integration

`runtime/source_selection.py` provides `SourceCandidate`, `select_source`, and distinct `SourceUnavailable` (`code=unavailable`), `SourceAmbiguous` (`code=ambiguous`), `InvalidSourceSelection` (`code=invalid_selection`). `SourceAmbiguous.candidates` contains source/ID/album/duration; an unmatched selector raises `InvalidSourceSelection` with the available eligible choices. The helper deduplicates **only** exactly repeated `(provider, stable ID)` entries with identical metadata, rejects conflicting metadata, requires exact normalized title and artist, finite full-song duration in configured range and known positive byte size <= configured cap. It accepts an explicitly supplied exact source ID (and provider to resolve ID collisions) or exact normalized album **only if uniquely identifying**. It never picks by duration cluster, album ranking or provider popularity. Unknown sizes fail closed; obtain trusted metadata before use, not fabricated estimates. If source metadata lacks duration/size (as upstream `SongInfo` does), first enrich it from an authorized provider or retain an explicit unavailable status; do not relax bounds to imitate upstream's first-result selection.

Lead-only integration steps: replace `worker.select_release` and its false studio-selection reason with a `select_source` call after mapping musicdl candidates to `SourceCandidate`; preserve the original musicdl object through `(source, identifier)` lookup, including explicit album/source-ID inputs in the command/tool and bounded worker argument passing. Surface ambiguity albums/IDs/durations to the user **before** starting expensive rendering or downloading, so they can choose explicitly; persist selected source ID/album in result/cache identity (and distinguish full song from excerpts). Translate the three error codes to actionable messages without leaking URLs/cookies. Keep the native-only override and provider entitlement checks; no musicdl third-party unlockers or unauthorized login. Continue hard byte/time limits, single-thread bounded download, fail on absent native URL, verify downloaded file containment, decoded duration versus metadata, full-song length and size before caching/rendering. The helper does not verify the media itself, guarantee studio provenance or grant downloading rights.

Tests are offline and cover exact-ID dedup, duration-cluster Pinkpop ambiguity, explicit selectors, namespace collisions, filtering, conflict and typed errors. Worker/plugin/backend integration, music-provider behavior and online acceptance remain untested and owned by Lead.
